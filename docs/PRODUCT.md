# Продукт: passwordless-аутентификация «из коробки»

> **Статус документа:** продуктовое видение и roadmap. Рабочая реализация v0.1 — в `authlayer/`; фактические возможности и ограничения — в `PROJECT_STATE.md` и `authlayer/docs/IMPLEMENTATION.md`. Упоминания SMTP, recovery, step-up и passkeys уже реализованы; sealed delivery, SSH, legacy-брокер, multi-tenancy и OIDC — ещё нет.

Это уточнение видения после обсуждения. Главный сдвиг:

> Для нового приложения пароль не нужно «доставлять» или «шифровать». Его нужно **убрать совсем**. Пользователь вводит email → получает код/ссылку → создаёт passkey → дальше входит по Face ID/Touch ID. Пароля нет ни в базе, ни в письме, ни в голове пользователя.

`sealed delivery` (зашифрованный пароль в письме) и SSH-сертификаты остаются, но это **отдельные модули** для legacy-сайтов и инфраструктуры, а не ядро продукта.

---

## 1. Видение

Разработчик ставит библиотеку/контейнер и получает готовую аутентификацию:

- пользователь регистрируется только по email;
- пароль не создаётся и не запрашивается;
- вход — по passkey (Face ID, Touch ID, Windows Hello, PIN);
- если passkey недоступен — вход по одноразовому коду из email;
- сессия живёт 7 дней, привязана к устройству, отзывается;
- восстановление — через passkey на другом устройстве или recovery-код, а не через «сброс пароля»;
- разработчик не пишет ни криптографию, ни письма, ни UI.

Это не «менеджер паролей» и не «шифрование паролей». Это **passwordless authentication as a library**.

## 2. Пользовательский путь: девочка покупает сумку

```text
1. Открыла сайт магазина.
2. Нажала "Войти".
3. Ввела email.
4. Получила письмо с кодом (6 цифр) или ссылкой.
5. Ввела код / нажала ссылку.
6. Телефон/ноутбук предложил Face ID / Touch ID / Windows Hello.
7. Passkey создан. Пользователь вошёл.
8. Купила сумку.
9. В следующий раз — "Войти по Face ID", без email и без пароля.
```

Что она **не** делает:

- не придумывает пароль;
- не запоминает его;
- не нажимает «забыли пароль?»;
- не вводит код из Google Authenticator;
- не понимает, что такое хеш, ключ или WebAuthn.

Что она **может** сделать, если потеряла устройство:

- войти по email-коду на новом устройстве;
- подтвердить новое устройство passkey со старого;
- использовать recovery-код;
- подождать 24–72 часа, если нет ни того, ни другого (anti-fraud).

```bash

```

```tsx
// app/providers.tsx
import { AuthLayerProvider } from '@authlayer/next';

    <AuthLayerProvider appId="app_...">

    </AuthLayerProvider>

```

```tsx
// app/login/page.tsx
import { SignIn } from '@authlayer/next';

  return <SignIn />;
}
```

Всё. UI входа, email-код, passkey, сессия, восстановление — внутри.

### Вариант B. Docker-контейнер для любого стека

```bash

  -e AUTHLayer_APP_NAME="My Shop" \

```

Дальше — либо iframe/hosted page, либо OIDC, либо reverse proxy.


SDK для iOS/Android — позже; для MVP хватит PWA/браузера.

## 5. Как это безопасно без пароля

### 5.1. Email — только bootstrap

Email-код подтверждает, что у пользователя есть доступ к почте. Это нормально для первого входа и для низкорисковых покупок. Но email не должен оставаться единственным фактором навсегда.

После первого входа:

- создаётся passkey, привязанный к устройству;
- для нового устройства требуется passkey/подтверждение;
- email-код на новом устройстве может требовать задержку или дополнительное подтверждение;
- все действия — в аудите.

### 5.2. Passkey — основной фактор

Passkey:

- не передаётся по сети;
- привязан к origin;
- устойчив к фишингу;
- хранится в TPM/Secure Enclave/Keystore;
- может быть synced (iCloud/Google) или device-bound.

Для высокорисковых аккаунтов (деньги, админка) — политика device-bound passkey + attestation.

### 5.3. Сессия

- access — 10–15 минут;
- refresh — 7 дней, ротация;
- device binding — DPoP/DBSC;
- отзыв устройства — мгновенный;
- повторный WebAuthn для чувствительных действий.

### 5.4. Если email украли

Сценарий:

1. Атакующий получил доступ к почте.
2. Он может запросить код входа.
3. Но на новом устройстве вход требует passkey/подтверждения.
4. Если passkey нет — срабатывает задержка + уведомление на доверенное устройство.
5. Он не может сбросить пароль, потому что пароля нет.
6. Он может попытаться восстановить аккаунт — recovery-политика должна это блокировать.

Остаточный риск: если атакующий получил почту **до** создания passkey (на этапе регистрации), он может зарегистрироваться первым. Поэтому:

- email-код короткоживущий и одноразовый;
- уведомление о новом устройстве;
- для высокорисковых сервисов — подтверждение по SMS/другому каналу или ручная проверка;
- мониторинг аномалий.

### 5.5. Честные ограничения

- email-провайдер видит коды (но они одноразовые и короткоживущие);
- если почта скомпрометирована на этапе регистрации — риск есть;
- malware на устройстве может действовать от имени пользователя;
- recovery — самый слабый момент любой passwordless-системы;
- для legacy-сайтов пароль всё равно существует (отдельный модуль).

## 6. Про «микро-нейронку» в библиотеке

Идея понятна: сделать систему «умной», чтобы она сама решала, что делать. Но в аутентификации это опасно, если нейросеть принимает само решение о доступе.

Почему:

- аутентификация должна быть **детерминированной** и проверяемой: либо подпись верна, либо нет;
- модель можно обмануть (adversarial examples), она может ошибаться, её сложно аудировать;
- tiny-модель на клиенте можно извлечь и изучить;
- «чёрный ящик» нельзя сертифицировать;
- ложные срабатывания/отказы будут раздражать пользователей;
- безопасность не становится лучше от ML, если нет криптографической основы.

Где ML реально полезен:

| Задача | Можно ли ML |
|---|---|
| Решение «пускать/не пускать» | **нет**, только криптография + политика |
| Оценка риска (новый IP, аномалия) | да, как **сигнал** |
| Детект ботов/спама | да |
| Подбор шага аутентификации (passkey vs email) | да, как UX-оптимизация |
| Антифрод в платежах | да |
| Генерация текстов писем/локализация | да |

Правильная формула:

```text
доступ = криптографическая проверка AND политика AND (риск < порог)
```

ML может влиять на «риск» и «какой шаг предложить», но не заменяет проверку подписи.

Если хочется «умную» библиотеку, делать не нейронку в auth-пути, а:

- адаптивный UX: если браузер поддерживает passkey — предлагать passkey; если нет — email-код;
- risk-based step-up: подозрительный вход → попросить passkey/biometric;
- аномалии: новый город/устройство → уведомление;
- серверный risk engine (позже, можно готовый: Authsignal, Castle, SEON).

## 7. Архитектура

```text
┌─────────────────────────────────────────────────────────────┐
│                     AuthLayer (library/cloud)               │
│  email OTP · WebAuthn · sessions · devices · recovery · UI  │
└───────────────┬─────────────────────────────┬───────────────┘
                │                             │
      ┌─────────▼─────────┐         ┌─────────▼─────────┐
      │ React SDK /       │         │ Docker / OIDC /   │
      │ hosted pages      │         │ reverse proxy     │
      └─────────┬─────────┘         └─────────┬─────────┘
                │                             │
      ┌─────────▼─────────┐         ┌─────────▼─────────┐
      │ Ваше приложение   │         │ Любое приложение  │
      └───────────────────┘         └───────────────────┘

      Postgres · Redis · SES/Postmark · KMS
```

### Режимы

1. **Cloud (SaaS)** — быстро, но данные у вендора.
2. **Self-hosted Docker** — контроль, приватность.
3. **Embedded SDK** — библиотека внутри приложения.
4. **OIDC provider** — для существующих приложений.

### Минимальная модель данных

```text
users(id, email, status, created_at)
passkeys(id, user_id, credential_id, public_key, sign_count, transports, aaguid)
sessions(id, user_id, device_id, token_hash, expires_at, revoked_at, binding)
devices(id, user_id, name, platform, pub_key, status, last_seen)
email_tokens(id, user_id, token_hash, purpose, expires_at, used_at)
recovery_codes(id, user_id, code_hash, used_at)
audit_events(id, actor, action, result, ip, ua, metadata, created_at)
```

## 8. Что меняется в предыдущем плане

| Было | Стало |
|---|---|
| Ядро — sealed delivery паролей | Ядро — passwordless auth (email → passkey) |
| Пароль шифруется и доставляется | Пароля нет вообще |
| Legacy-брокер — часть ядра | Legacy-брокер — отдельный модуль |
| SSH — один из главных сценариев | SSH — отдельный модуль для инфры |
| Сложная криптография на первом месте | Простой UX и интеграция на первом месте |
| «Любое приложение» | «Любое приложение, которое ты пишешь» + gateway для существующих |

Что остаётся:

- passkeys/WebAuthn;
- device-bound sessions;
- 7 дней refresh;
- отзыв устройств;
- sealed delivery для legacy;
- SSH-сертификаты;
- аудит.

## 10. Конкуренты и ниша

| Продукт | Модель | Отличие AuthLayer |
|---|---|---|
| Clerk | SaaS, React-first | self-hosted, passwordless-first |
| Auth0/Okta | SaaS, enterprise | проще, дешевле, без паролей |
| Stytch (Twilio) | SaaS API | self-hosted, открытый |
| Hanko | open-source passkeys | проще для не-разработчиков, hosted UI |
| Ory Kratos | open-source identity | готовый UI/SDK, а не конструктор |
| Keycloak | enterprise IdP | не для consumer-сайтов, тяжёлый |
| Supabase Auth | BaaS | независимость, passwordless-first |

Ниша:

- indie-разработчики и малые SaaS;
- e-commerce/community, где пользователи не хотят пароли;
- self-hosted/privacy/EU;
- «поставил и забыл», а не «собери identity-платформу».

Рынок конкурентный. Дифференциация — **UX, простота установки, отсутствие пароля как принцип**, а не новая криптография.

## 11. Что не делать

- не писать свою WebAuthn-библиотеку;
- не писать свою криптографию;
- не хранить пароли;
- не делать email единственным фактором навсегда;
- не ставить нейросеть в решение о доступе;
- не обещать «любой чужой сайт без изменений»;
- не делать «ещё один Keycloak»;
- не начинать с enterprise-функций;
- не усложнять MVP.
